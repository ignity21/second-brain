* Scenarios
** Lazy Initialization
One particular case is that the shared data needs protection while it's being initialized.
*** Thread-safe Lazy Initialization
#+begin_src c++
  std::shared_ptr<some_resource> resource_ptr;
  std::mutex resource_mutex;

  // could optimized by using infamous  double-checked locking pattern.
  void foo() {
    std::unique_lock<std::mutex> lk(resource_mutex);
    if (!resource_ptr) {
      resource_ptr.reset(new some_resource);
    }
    lk.unlock();
    resource_ptr->do_something();
  }
#+end_src
- using ~std::once_flag~ and ~std::call_once~ *Recommended*
#+begin_src c++
  std::shared_ptr<some_resource> resource_ptr;
  std::once_flag resource_flag;

  void init_resource() {
    resource_ptr.reset(new some_resource);
  }

  void foo() {
    std::call_once(resource_flag, init_resource);
    resource_ptr->do_something();
  }
#+end_src
** Rarely Updated Data
Use reader-writer mutex
- exclusive access by a single "writer" thread
- concurrent access by multiple "reader" threads
*** Implementation
- C++17 provides ~std::shared_mutex~ and ~std::shared_timed_mutex~
- C++14 only features ~std::shared_time_mutex~
- ~std::lock_guard~ and ~std::unique_lock~ for "writer"
- ~std::shared_lock~ for "readers"
