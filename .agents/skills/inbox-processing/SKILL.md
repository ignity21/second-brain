# 处理收件箱

`inbox/` 位于仓库根目录（已 gitignore），存放待处理的原始材料；与 `roamnotes-v2/Unsorted/`（未分类的正式笔记）无关。只处理 `inbox/` 根下的文件，`archive/` 等子目录不管。

## 材料约定

一份材料一个文件，如 `inbox/tcp-handshake.md`，放在 `inbox/` 根下，不建子目录，文件名能认出主题就够。网页材料通常是浏览器「summarize page」生成的总结；也可以是原文、文稿或幻灯片 PDF。

各领域的学习角度、用途和档位记录在 [`.agents/learning-goals.md`](../../learning-goals.md)，同一领域可按子领域分档。档位（不需要 / 知道 / 能判断 / 能写）的定义见 `cc-note-writing`「掌握目标与载体」。

## Review 原材料

review 和用户一起把原材料改成写笔记用的预处理稿，不直接产出笔记；归档时保留的就是这份预处理稿。

- **分块**：按标题或小节分块，PDF 按页或几页一块；一次给用户一块，先贴出这一块的原文（太长时贴到足以对照判断），再给判断，不让用户回翻原文件。
- **每块附 AI 的判断**：核对结论（错误、存疑、与已有笔记冲突）和拟收 / 不收（按档位），以及准备怎么改；需要画流程、时序、状态图时，直接在预处理稿里写 PlantUML block（Markdown 也能渲染），写笔记时搬运或调整。
- **逐块确认**：给出这一块的判断或反馈后，停下等用户确认，再进入下一块；用户可能基于反馈提出新问题或补充。不要在同一轮里一边给反馈一边抛出下一块。
- **就地修改**：用户提出卡点或意见时当场讨论，结论写回这一块：
  - 错误直接改正；与已有笔记冲突的按用户裁决改。
  - 超出档位、不收的内容删掉。
  - 用户的卡点、想法和已解答的疑问用原话写在相关段落后：`> 卡点：原来以为 X，实际 Y`（答不上来就写「答不上来」）、`> 想法：...`、`> 疑问：... —— 解答：...`。原话只是素材，写笔记时再归纳。
  - AI 无法核实、又不能自己决定的写成 `TODO verify: ...`。
- **跳过**：用户说「剩下都没问题」时，剩余块按 AI 的判断修改，直接收口。
- PDF 等不能直接编辑的材料，在旁边建同名 `.md` 存放预处理稿。

## 向用户提问

只问答案会改变产出的问题。不问 AI 能自己核实或决定的事：事实对错（先自己核对）、笔记位置和标题（决定后在回复里说明）。

- **review 前**：领域角度、用途与档位，仅当该领域或子领域不在 `learning-goals.md` 中，或材料明显超出已记录的用途时问；一次问清，最多 3 个。
- **review 中**：卡点由用户随块提出；冲突与存疑在对应块问以哪个为准。
- **收口**：全部块走完后问一次「卡点都提完了吗？还有要补充的吗？」。档位为「能判断」或「能写」且材料涉及选择时，同时问打算用在哪里、有什么约束。卡点常零散出现，得到确认后才写笔记，不自己假定收集结束。

写笔记时，回答的去处：

| 回答 | 记录位置 |
|---|---|
| 领域角度、用途、子领域档位 | `.agents/learning-goals.md`（写明日期；用户随时可改） |
| 原来的错误理解 | 笔记模板的误解章节（`Misconceptions` / `Pitfalls` / `Corrected Model`），并做卡片 |
| 答不上来、没懂 | 正文对应章节写清楚，不在误解章节复述，并做卡片 |
| 个人经验、想法、项目选择及理由 | 笔记的 `My Take :mine:`，归纳润饰（见 `cc-note-writing`「人机分工」） |
| 冲突裁决 | 直接修正笔记，不另记 |
| 只对这次处理有用的背景 | 不记 |

## 流程

1. 列出 `inbox/` 根下的文件；有多个时让用户选一个，一次处理一份。
2. 读取材料和 `learning-goals.md`，检索已有笔记，判断是新内容、补充还是与旧笔记冲突。
3. review 前提问（见上节）。
4. 逐块 review，把原材料改成预处理稿（见「Review 原材料」），然后收口。
5. **按目标写笔记**：以预处理稿为输入（`cc-note-writing`；优先合并到已有笔记，索引遵循 AGENTS.md）：
   - 以目标档位和用户卡点为界：只展开该档位需要或用户问到的内容。
   - 「不需要」：不收，在回复里说明。
   - 「知道」：只写「问题 → 机制」及一句话说明，合并进该领域的概览笔记；没有概览笔记时新建，放进合适的大类或 `Unsorted/`。
   - 「能判断」：写核心模型、对比、判断和故障。「能写」另加核心词汇或模板代码。用户的错误理解写成「原来以为 X → 实际 Y → 最小例子」；答不上来的点在正文对应章节写透。
   - 换个时间问 AI 一次就能答对、又不属于目标档位的内容不收；0 条产出是正常结果。
   - 预处理稿里的 `> 疑问：… —— 解答：…` 在笔记中改写为陈述知识的正文，不保留问答形式；问答形式只用于卡片。
   - review 中用 show-me 做的 HTML 演示，保留的复制到本大类 `demos/`，笔记用 `[[file:...]]` 链接，旁边配一张 PlantUML 静态图或表格，不打开 HTML 也能看懂。
   - 预处理稿是 Markdown，搬进 Org 时转换语法：`>` 引用改为段落或列表，反引号代码改为 `~code~`，代码块改为 `#+begin_src`。
6. **验证**：按 AGENTS.md「按改动验证」检查本次改动的笔记与索引（含生成 PlantUML 图片），执行 `org-roam-db-sync`，无法执行时说明原因。
7. **出题巩固**（`anki-cards` skill；目标 Deck 的规则以该 skill 为准）：
   - 每个卡点直接做一张卡，不再为它出题。
   - 用途含面试时，该领域的面试常见问题即使用户没问过，也整理成问答卡片。
   - 卡点以外的要点出最多 3 道题，一次一道；用户可以作答，也可以跳过。题目连同答案做成卡片。
   - 题目要能脱离笔记独立读懂，答案在笔记里能找到；「知道」档只考「什么问题 → 用什么机制」。
   - 用户答错时，先检查笔记是否没写清楚，必要时修正；答错的点按卡点记录。
8. **归档**：预处理稿只是写笔记的输入，归档前不再回改，与笔记不一致时以笔记为准。把预处理稿（连同 PDF 等原件）移到 `inbox/archive/YYYYmmdd/`（当天日期，目录不存在就创建；重名时加 `-2` 等后缀）；删除 `inbox/archive/` 下日期距今超过 10 天的 `YYYYmmdd` 目录。
9. 回复列出：新增或修改的笔记、生成的卡片、记录到 `learning-goals.md` 的内容、没有收录的部分及原因。
