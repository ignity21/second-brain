# 库 / 工具笔记

适用于第三方库、CLI 工具、框架，例如 Polars、uv、websockets。

**默认档位**：主体是「知道」和「能判断」；「能写」只覆盖核心词汇。

## 模板

```org
:PROPERTIES:
:ID:       <uuid4>
:VERIFIED_WITH: <Name> <version> (<YYYY-MM-DD>)
:END:
#+title: <Name>

* Positioning      ; 解决什么问题；什么时候选它、什么时候不选
* Mental Model     ; 核心抽象和运作方式，读懂后能推出大部分 API
* Coming from <X>  ; 用户已掌握的相近工具要改掉的习惯，链接 X 的笔记
* Core Vocabulary  ; 按任务组织的高频 API 表（能写）
* Distinctions     ; 相似选项的对比表
* Pitfalls         ; 坑、版本漂移、AI 易错写法
* Capability Map   ; 其他能力：名字 + 一句话 + 何时想到它（知道）
* My Take :mine:   ; 用户的取舍和经验
```

库较大时按主题拆成多篇（例如「Time Series with Polars」）。主题笔记沿用同一模板，省略 `Positioning` 和 `Coming from`（除非该主题有特有的迁移问题），由主笔记或其下的 APIs 索引收录，开头不回链主笔记（见 AGENTS.md「笔记间链接」）。

## 各章节要求

- **Mental Model**：写出让 API 变得可预测的规则，而不是功能列表。好的检验标准是：读者没见过某个 API，也能猜到它的行为或该去哪里找。例如 Polars 的「表达式只是描述，上下文决定如何求值和输出长度」。
- **Coming from**：只在用户确实掌握相近工具时写（查全库笔记确认）。用三列表：旧习惯 | 新写法 | 原因或后果。
- **Core Vocabulary**：每篇 10～30 条，按工作流顺序排列任务，例如检查 → 选择 → 变换 → 合并 → 汇总。列为「Task | Code」，必要时加一列备注。只收录需要脱手写出的高频操作，低频 API 放能力地图或直接删除。代码里有 `|` 时移到表外，避免破坏 Org 表格。
- **Distinctions**：每张表回答一个「该用哪个」的问题，列出差别和适用条件。边界行为（区间开闭、默认值）用最小示例加结果展示。
- **Pitfalls**：每条写成「陷阱 → 原因 → 正确做法」。版本漂移单独做表：「旧写法（AI 常写）| 当前写法 | 备注」，表头写明版本。
- **Capability Map**：一行一项，只有名字、一句话用途、何时想到它，不写用法细节。

## 不记

- 照抄的 API 参数表、安装命令（除非有用户自己的配置选择）、只演示一个函数调用的示例。
- 与本库无关的周边内容（例如课程里顺带的绘图代码），属于其他库的另写或删除。
