#+title: Error Handling Design
#+filetags: :SystemDesign:

* 两种方式
| | 错误码 / 返回值 | 异常 |
|---|---|---|
| 调用方 | 每次调用后都要检查，忘了检查就静默出错 | 不处理就沿调用栈向上传播，不会被静默忽略 |
| 正常路径 | 与错误处理代码混在一起 | 正常路径清晰，错误处理集中 |
| 跨边界 | RPC、跨语言、C 接口只能用返回码 | 不能跨进程或语言边界传播 |
| 性能 | 开销可预测 | 抛出时开销大，不适合频繁发生的情况 |

选择：不期望发生的事用异常；可预期、调用方必须处理的结果（如「没找到」「余额不足」）用返回值，现代语言里常写成 ~Result~ / ~Optional~ 类型。受条件限制只能用一种时（如 RPC 只能用返回码）就统一用那一种。

* 资源清理
出错时提前返回或抛异常，已获取的资源（锁、文件、连接）必须释放。各语言的手段：
- C++：RAII，析构函数释放，见 [[id:474df27e-ed1f-42f0-997f-633339b91cb5][C++ RAII and Smart Pointers]]
- Java、Python： ~finally~ 块、 ~try-with-resources~ / ~with~ 语句
- Go： ~defer~
- C： ~goto fail~ ，在函数末尾集中清理

* 错误分类
| 类别 | 例子 | 处理 |
|---|---|---|
| 资源错误 | 网络故障、内存耗尽、栈溢出、磁盘满 | 关键资源出错时报错并停止运行；环境中的暂时性问题（超时、连接断开）重试，带退避和次数上限 |
| 程序错误 | 空指针、非法参数、违反不变式 | 是 bug，重试没有用：记录日志并告警，尽早失败（fail fast）便于定位 |
| 用户输入错误 | 格式不对、越界的值 | 返回明确的错误给客户端；统计错误率，帮助改进产品和发现恶意请求 |

重试会放大故障，对哪些错误重试、重试多少次的取舍见 [[id:28a88260-5abb-48a9-bf27-5678acd7be3b][Reliability and Availability]]。
