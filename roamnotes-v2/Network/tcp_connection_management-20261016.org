* Intuition

TCP 提供面向连接、可靠的字节流传输。它假设网络会出现丢包、乱序、延迟和拥塞，用五类机制分别应对：

| 机制                 | 解决的问题                           |
|----------------------+--------------------------------------|
| 序号 + 确认号（ACK） | 顺序控制：乱序重排、判断哪些已收到   |
| 超时重传             | 可靠传输：丢包                       |
| 状态机               | 连接维护：建立与关闭                 |
| 接收窗口             | 流量控制：发送方不超过接收方处理能力 |
| 拥塞控制             | 调整发送速率，避免加剧网络拥塞       |

本笔记只讲连接维护。核心模型：「连接」不是物理线路，而是 *两端各自维护的一份状态* （序号、窗口、当前状态）；中间的路由器只转发报文，不知道连接存在。因此：

- 建立和关闭连接，就是让两端的状态同步变化；
- 连接异常，几乎都是「两端状态对不上」，表现为某一端卡在某个状态。用 ~ss -tan~ 看状态分布，就能反推是哪一步出了问题。

* 三次握手

目的：建立连接、确认双方收发能力、交换初始序列号（ISN）。

1. SYN：客户端发自己的 ISN。
2. SYN + ACK：服务端确认，并发送自己的 ISN。
3. ACK：客户端确认；服务端收到后连接建立完成。

** 为什么是三次

三次是让 *双方都确认「我能发、对方能收」* 并 *同步双方 ISN* 的最小交互次数：

- 第 1 次后：服务端知道「客户端能发」。
- 第 2 次后：客户端知道「服务端能收（ACK 了我的 SYN），也能发」。
- 第 3 次后：服务端才知道「客户端能收」（客户端 ACK 了它的 SYN）。

两次不够的直接后果是 *旧 SYN 会建出假连接* ：网络里滞留的旧 SYN 迟到，服务端回 SYN + ACK 后就认为连接已建立，开始为一条谁也不要的连接分配资源。有第 3 次时，客户端收到不认识的 SYN + ACK 会回 RST，服务端据此丢掉这条连接。

更多次没有意义：两端都已各自完成一次「发出去 → 收到回应」，第 4 次不会带来新信息。

握手确认的是 *此刻双向可达* ，不是某条固定通路（路由逐包变化），也不保证后续数据一定送达，那由 ACK 和超时重传负责。

** 初始序列号为什么不能固定

两个原因：

- 防混淆：同一四元组（双方 IP + 端口）的新旧连接如果都从相同序号开始，旧连接迟到的报文可能正好落在新连接的接收窗口里，被当成新数据。
- 防伪造：ISN 可预测时，攻击者不必看到流量就能构造出序号正确的报文，向连接注入数据或用 RST 掐断它。

现代实现（RFC 6528）用「随时间增长的计数器 + 四元组与密钥的哈希」生成 ISN：同一四元组的序号随时间推进，外人又猜不出来。

* 连接关闭（四次挥手）

TCP 全双工，两个方向可独立关闭：

1. FIN：A 表示自己不再发送数据。
2. ACK：B 确认收到 FIN；此时 A → B 方向已关闭，B → A 方向仍可发数据（半关闭）。
3. FIN：B 发完剩余数据，也请求关闭。
4. ACK：A 确认 B 的 FIN，随后进入 TIME_WAIT。

** 为什么是四次

- 一条连接 = 两个独立方向。关闭一个方向要一轮「FIN + ACK」，两个方向各一轮：2 个 FIN + 2 个 ACK = 4。
- 第 2、3 步分开，是因为 B 收到 FIN 时可能还有数据没发完：先 ACK 掉 A 的 FIN，发完数据，再发自己的 FIN。
- B 恰好没有待发数据时，ACK 和 FIN 合进同一个报文，挥手就只有 3 个报文。

** 时序与序号

FIN 与 SYN 一样各占一个序列号：B 的 FIN 序号 = B 最后发出的数据字节 + 1，A 用 ~w+1~ 确认它。

* 连接状态

每个状态是 *一端* 的状态；同一时刻两端状态不同（A 在 ~FIN_WAIT_2~ 时，B 正在 ~CLOSE_WAIT~ ）。不要理解成一条连接依次走过表里所有状态。

| 状态          | 含义                                 |
|---------------+--------------------------------------|
| ~CLOSED~      | 连接不存在或已经关闭                 |
| ~LISTEN~      | 服务端监听连接请求                   |
| ~SYN_SENT~    | 客户端已发送 SYN，等待响应           |
| ~SYN_RECV~    | 服务端已收到 SYN，等待最终 ACK       |
| ~ESTABLISHED~ | 连接建立，可以正常通信               |
| ~FIN_WAIT_1~  | 主动关闭方已发送 FIN，等待确认       |
| ~FIN_WAIT_2~  | 对方已确认 FIN，等待对方关闭         |
| ~CLOSE_WAIT~  | 被动关闭方收到 FIN，等待本地应用关闭 |
| ~LAST_ACK~    | 被动关闭方发送 FIN，等待最终 ACK     |
| ~TIME_WAIT~   | 主动关闭方等待一段时间后彻底关闭     |

#+begin_src plantuml
@startuml
[*] --> CLOSED
CLOSED --> LISTEN : listen()
CLOSED --> SYN_SENT : connect()
LISTEN --> SYN_RECV : 收 SYN
SYN_SENT --> ESTABLISHED : 收 SYN+ACK
SYN_RECV --> ESTABLISHED : 收 ACK

ESTABLISHED --> FIN_WAIT_1 : 发 FIN（主动关闭）
FIN_WAIT_1 --> FIN_WAIT_2 : 收 ACK
FIN_WAIT_2 --> TIME_WAIT : 收 FIN
TIME_WAIT --> CLOSED : 等 2MSL

ESTABLISHED --> CLOSE_WAIT : 收 FIN（被动关闭）
CLOSE_WAIT --> LAST_ACK : 应用 close()，发 FIN
LAST_ACK --> CLOSED : 收 ACK
@enduml
#+end_src

两条转移链比记整张表省事：

- 主动关闭方： ~ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED~
- 被动关闭方： ~ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED~

谁先发 FIN 谁就是主动关闭方，客户端和服务端都可能。状态名自带信息： ~_WAIT~ 是「等」； ~CLOSE_WAIT~ 是「对端已关、等我方应用关」。

** TIME_WAIT 为什么等 2MSL

MSL（Maximum Segment Lifetime）是报文段在网络中的最大生存时间。TIME_WAIT 有两个目的：

- 可靠关闭：最终 ACK 丢失时，对方会重传 FIN；本端还留着连接状态，能再回一次 ACK。若本端已经 CLOSED，只能回 RST，对方会把正常关闭当成出错。
- 清除旧报文：等这条连接在两个方向上滞留的报文都从网络消失，同一四元组的新连接才不会收到它们。

为什么是 2MSL 而不是 1MSL：最坏情况下，最终 ACK 要 1 个 MSL 才到对端（或在途中丢失），对端随后重传的 FIN 又要 1 个 MSL 才回到本端；等 2MSL 才覆盖这一整轮往返。

Linux 不按 MSL 计算，TIME_WAIT 固定 60 秒（内核常量 ~TCP_TIMEWAIT_LEN~ ，没有 sysctl 可调）。

* 异常与排查

| 现象            | 卡在的状态                          | 原因与处理                                                              |
|-----------------+-------------------------------------+-------------------------------------------------------------------------|
| 握手报文丢失    | 客户端 ~SYN_SENT~ ，服务端 ~SYN_RECV~ | 客户端重传 SYN，服务端重传 SYN + ACK，次数用尽后放弃                     |
| 大量 ~SYN_RECV~ | 服务端 ~SYN_RECV~                   | SYN flood，见下文                                                        |
| 大量 ~CLOSE_WAIT~ | 被动方 ~CLOSE_WAIT~               | 本方应用没 ~close()~ ，修代码                                            |
| 大量 ~TIME_WAIT~ | 主动方 ~TIME_WAIT~                 | 短连接太多，改成复用连接                                                 |
| 对端已消失      | 本端仍 ~ESTABLISHED~                | 半开连接，靠重传超时、Keepalive 或应用层心跳发现                         |
| 最终 ACK 丢失   | 对端 ~LAST_ACK~                     | 对端重传 FIN，本端在 TIME_WAIT 期间重新 ACK；这正是 TIME_WAIT 存在的理由 |

** CLOSE_WAIT 与 FIN_WAIT_2 堆积

~CLOSE_WAIT~ 堆积是 *收到 FIN 那一方应用的 bug* ：内核已经替应用回了 ACK，状态停在 ~CLOSE_WAIT~ 等应用调用 ~close()~ ；应用不关，它就一直在，内核没有超时，调参数也没用。排查方向是检查所有代码路径（异常分支、连接池归还）是否都关闭了 socket。

对端的表现取决于它是怎么关的：

- 调 ~close()~ 关闭：对端成为「孤儿」 ~FIN_WAIT_2~ （应用已不再持有它），内核在 ~tcp_fin_timeout~ （默认 60 秒）后回收。所以 ~CLOSE_WAIT~ 可以长期堆积，对端的 ~FIN_WAIT_2~ 却会自己消失。
- 用 ~shutdown(SHUT_WR)~ 只关写方向：应用仍持有 socket，等着读对方的数据，对端的 ~FIN_WAIT_2~ 没有超时，会和 ~CLOSE_WAIT~ 一起长期存在。

本机实测：两种关闭方式下 ~ss -tano~ 中，孤儿 ~FIN_WAIT_2~ 带 60 秒计时器，半关闭的 ~FIN_WAIT_2~ 和 ~CLOSE_WAIT~ 都没有计时器。

** TIME_WAIT 堆积

TIME_WAIT 出现在主动关闭方：客户端主动关就堆在客户端，服务端主动关（例如每个响应后断开的 HTTP 服务）就堆在服务端。

危害取决于在哪一端：

- 客户端：连同一个目标 ~IP:端口~ 时，四元组只有本地端口在变。每条 TIME_WAIT 占住一个本地端口 60 秒，短连接一多，本地端口范围（默认 32768–60999，约 2.8 万个）耗尽， ~connect()~ 报 ~EADDRNOTAVAIL~ 。
- 服务端：本地 ~IP:端口~ 固定、对端各不相同，不消耗端口，通常只占些内存，一般无害。

处理：

- 根本办法是复用连接：HTTP keep-alive、连接池，减少短连接。
- 客户端可开 ~tcp_tw_reuse~ ，允许新的出站连接复用处于 TIME_WAIT 的端口（依赖 TCP 时间戳判断新旧报文；当前内核默认值 2 表示只对回环地址启用）。
- 服务端重启时 ~bind()~ 报 ~EADDRINUSE~ （旧连接还在 TIME_WAIT）：监听 socket 设 ~SO_REUSEADDR~ 。

坑（网上和 AI 的旧答案里常见）：

- 调小 ~tcp_fin_timeout~ 不会缩短 TIME_WAIT，它管的是孤儿 FIN_WAIT_2。
- ~tcp_tw_recycle~ 会让 NAT 后面的客户端连不上，Linux 4.12 已删除。
- 用 ~SO_LINGER~ 超时 0 关闭，会发 RST 跳过 TIME_WAIT，也就丢掉了它的两项保护。

** 半开连接与 Keepalive

半开连接：对端宕机或断网，没来得及发 FIN 或 RST，本端仍停在 ~ESTABLISHED~ 。能不能发现，取决于本端在做什么：

- 本端在发数据：收不到 ACK，按指数退避重传， ~tcp_retries2~ （默认 15）次后放弃，约 15 分钟后报 ~ETIMEDOUT~ 。
- 对端已经重启：它已不知道这条连接，收到数据回 RST，本端立刻报 ~ECONNRESET~ 。
- 本端只在等读：永远发现不了，需要 Keepalive 或应用层心跳。

TCP Keepalive：

- *每个 socket 默认关闭* ，应用要设 ~SO_KEEPALIVE~ 才生效（本机实测 ~getsockopt~ 返回 0）。
- 开启后，空闲 ~tcp_keepalive_time~ 才开始探测，每隔 ~tcp_keepalive_intvl~ 发一次，连续 ~tcp_keepalive_probes~ 次无响应就断开。内核默认 7200 秒 / 75 秒 / 9 次，即空闲 2 小时后再约 11 分钟才判定断开。Arch 系发行版把 ~tcp_keepalive_time~ 改成了 120 秒（ ~/usr/lib/sysctl.d/10-arch.conf~ ），本机读到的是这个值。也可以用 ~TCP_KEEPIDLE~ 等选项按 socket 设置。
- 它只能证明对端内核还在，不能证明对端应用正常。需要快速、可靠地发现断线时，用应用层心跳。

** SYN Flood 与两个队列

服务端为每个监听 socket 维护两个队列：

| 队列                 | 里面是什么                                  | 上限                                |
|----------------------+---------------------------------------------+-------------------------------------|
| SYN 队列（半连接）   | 收到 SYN、已回 SYN + ACK 的 ~SYN_RECV~ 连接 | 与 ~tcp_max_syn_backlog~ 和 backlog 有关 |
| accept 队列（全连接） | 握手完成、等应用 ~accept()~ 的连接          | ~min(backlog, somaxconn)~           |

- SYN flood：攻击者用伪造源地址大量发 SYN，从不完成第三步，占满 SYN 队列，正常连接进不来。防御是 SYN cookies（ ~tcp_syncookies~ 默认 1，队列溢出时启用）：服务端不再保存半连接，把连接参数编码进 SYN + ACK 的 ISN，收到合法的第三次 ACK 时再从确认号里还原出来。
- accept 队列满（应用 ~accept()~ 太慢）：Linux 默认丢弃第三次 ACK，客户端以为连接已建立，发出的请求却迟迟没有响应。 ~ss -lnt~ 中 LISTEN 行的 Recv-Q 是当前 accept 队列长度，Send-Q 是上限。

* Misconceptions

** ACK 和 FIN 分开发，是给对方留窗口期吗？

原来以为：被动方先 ACK、过一会儿再发 FIN，是主动方「给」对方一段时间把数据发完。

实际：主动方的 FIN 只关闭自己的发送方向，从来不限制对方发数据。ACK 和 FIN 分开，纯粹因为被动方自己还有数据要发；没有数据时两者合并成一个报文，挥手只有 3 个报文。FIN 的序号排在被动方最后的数据之后，所以对方能确认数据已经收全。

例子：客户端发完请求后 ~shutdown(SHUT_WR)~ （发 FIN），服务端照常把整个响应发完，再发自己的 FIN。

* My Take :mine:

- 握手就是一次双向连通测试：每一端都要亲眼看到「自己发出去的东西得到了回应」才算数。客户端发 SYN、收到 SYN + ACK，完成了自己的一来一回；服务端发 SYN + ACK、收到最后的 ACK，完成了它的一来一回。哪一端发不出、收不到，或者中间路由不通，都会在这两次往返里暴露。两端各验证过一次往返就够了，再多来回也测不出新东西。
- 挥手就是两边各自宣布「我不再发了」（FIN），再各自确认对方的宣布（ACK）。两份宣布互不依赖，所以是两对 FIN + ACK。
