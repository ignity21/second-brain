* Intuition

TCP 提供面向连接、可靠的字节流传输。它假设网络会出现丢包、乱序、延迟和拥塞，用五类机制分别应对：

| 机制                 | 解决的问题                       |
|----------------------+----------------------------------|
| 序号 + 确认号（ACK） | 顺序控制：乱序重排、判断哪些已收到 |
| 超时重传             | 可靠传输：丢包                    |
| 状态机               | 连接维护：建立与关闭               |
| 接收窗口             | 流量控制：发送方不超过接收方处理能力 |
| 拥塞控制             | 调整发送速率，避免加剧网络拥塞      |

「连接」不是物理连接，而是 *两端各自维护的一份状态机* （序列号、窗口、当前状态）；中间的路由器只转包、不认连接。因此这类异常大多是「两端状态不一致」。

* 三次握手

目的：建立连接、确认双方收发能力、交换初始序列号（ISN）。

1. SYN：客户端发自己的 ISN。
2. SYN + ACK：服务端确认，并发送自己的 ISN。
3. ACK：客户端确认；服务端收到后连接建立完成。

** 为什么是三次

三次是让 *双方都确认「我能发、对方能收」* 并 *同步 ISN* 的最小交互次数：

- 第 1 次后：服务端知道「客户端能发」。
- 第 2 次后：客户端知道「服务端能发，也能收」（已 ACK 我的 SYN）。
- 第 3 次后：服务端才知道「客户端能收」（客户端 ACK 了它的 SYN）。

两次不够：服务端一发出 SYN+ACK 就认为连接建立，一个延迟到达的旧 SYN 会让它凭空建出一条谁也不认的连接；有了第 3 次 ACK，客户端对不认识的 SYN+ACK 回 RST，服务端就能发现这条是假的。更多次则没有新信息。

注意：确认的是 *此刻双向可达* ，不是某条固定通路（路由逐包变化）；握手也不保证后续数据一定送达，那由 ACK 与超时重传负责。

** 初始序列号为什么不能固定

如果每次连接都从相同序号开始，旧连接中延迟到达的报文可能被当成新连接的数据。TCP 用变化的 ISN 降低这种混淆。

* 连接关闭（四次挥手）

TCP 全双工，两个方向可独立关闭，正常断开需要四次交互：

1. FIN：A 表示自己不再发送数据。
2. ACK：B 确认收到 FIN，但仍可继续发送数据。
3. FIN：B 完成数据发送后，也请求关闭。
4. ACK：A 确认 B 的 FIN，随后进入 TIME_WAIT。

B 收到 FIN 后连接进入半关闭：A 不再发送数据，但仍能接收 B 的数据。

** 为什么是四次

- 一条连接 = 两个独立方向，关闭一个方向要一轮「FIN + ACK」，两个方向各一轮，所以是 2 个 FIN + 2 个 ACK = 4。
- 不是固定三次：B 收到 A 的 FIN 时可能还有数据没发完，要先 ACK 掉 A 的 FIN、发完剩余数据，再发自己的 FIN。B 恰好没有待发数据时，ACK 和 FIN 合进同一个包，就只有三个报文。
- 不是「A 给 B 一个窗口期」：A 的 FIN 只表示 A 不再发数据，不影响 B 照常发；ACK 和 FIN 分开只是因为 B 自己还没发完。

** 时序与序号

#+begin_src plantuml
@startuml
participant A
participant B
A -> B : data ...
B -> A : data ...
A -> B : FIN seq=u
note right of A : A 不再发数据
B -> A : ACK ack=u+1
note right of B : 有数据就继续发
B -> A : data ...
B -> A : FIN seq=w
A -> B : ACK ack=w+1
note over A : TIME_WAIT，等 2MSL 后 CLOSED
note over B : 收到 ACK 后 LAST_ACK → CLOSED
@enduml
#+end_src

FIN 与 SYN 一样各占一个序列号：B 的 FIN 序号 = B 最后发出的数据字节 + 1，A 用 ~w+1~ 确认它。

* 连接状态

每个状态是 *一端* 的状态；同一时刻两端状态不同（A 在 ~FIN_WAIT_2~ 时，B 正在 ~CLOSE_WAIT~ ）。不要理解成一条连接依次走过表里所有状态。

| 状态          | 含义                                 |
|---------------+--------------------------------------|
| ~CLOSED~      | 连接不存在或已经关闭                  |
| ~LISTEN~      | 服务端监听连接请求                    |
| ~SYN_SENT~    | 客户端已发送 SYN，等待响应             |
| ~SYN_RECV~    | 服务端已收到 SYN，等待最终 ACK         |
| ~ESTABLISHED~ | 连接建立，可以正常通信                 |
| ~FIN_WAIT_1~  | 主动关闭方已发送 FIN，等待确认          |
| ~FIN_WAIT_2~  | 对方已确认 FIN，等待对方关闭            |
| ~CLOSE_WAIT~  | 被动关闭方收到 FIN，等待本地应用关闭     |
| ~LAST_ACK~    | 被动关闭方发送 FIN，等待最终 ACK        |
| ~TIME_WAIT~   | 主动关闭方等待一段时间后彻底关闭         |

#+begin_src plantuml
@startuml
[*] --> CLOSED
CLOSED --> LISTEN : listen()
CLOSED --> SYN_SENT : connect()
LISTEN --> SYN_RECV : 收 SYN
SYN_SENT --> ESTABLISHED : 收 SYN+ACK
SYN_RECV --> ESTABLISHED : 收 ACK

ESTABLISHED --> FIN_WAIT_1 : 发 FIN（主动关闭）
FIN_WAIT_1 --> FIN_WAIT_2 : 收 ACK
FIN_WAIT_2 --> TIME_WAIT : 收 FIN
TIME_WAIT --> CLOSED : 等 2MSL

ESTABLISHED --> CLOSE_WAIT : 收 FIN（被动关闭）
CLOSE_WAIT --> LAST_ACK : 应用 close()，发 FIN
LAST_ACK --> CLOSED : 收 ACK
@enduml
#+end_src

两条转移链比记整张表省事：

- 主动关闭方： ~ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED~
- 被动关闭方： ~ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED~

状态名自带信息： ~_WAIT~ 是「等」； ~CLOSE_WAIT~ 是「对端已关、等我方应用关」。

** TIME_WAIT 为什么等 2MSL

MSL（Maximum Segment Lifetime）是报文段在网络中的最大生存时间。TIME_WAIT 有两个目的：

- 保证正常关闭：最终 ACK 丢失时，对方会重传 FIN，本端还有机会再确认。
- 避免旧报文干扰新连接：让旧连接滞留的报文有时间从网络消失。

为什么是 2MSL 而不是 1MSL：1 个 MSL 留给最终 ACK 传到对端，另 1 个 MSL 留给对端可能重传的 FIN 返回。

* 异常与处理机制

核心模型：异常大多表现为「连接卡在某个状态」，看状态堆积就能反推是哪一步缺失。

| 异常                        | 卡在的状态                              | 处理                   |
|-----------------------------+----------------------------------------+------------------------|
| 握手报文丢失                 | ~SYN_SENT~ / ~SYN_RECV~                 | 超时重传 SYN           |
| 长期无数据、对端可能已消失     | ~ESTABLISHED~ （半开连接）              | TCP Keepalive 探测     |
| 被动关闭方应用没 ~close()~    | 被动方 ~CLOSE_WAIT~ ；主动方 ~FIN_WAIT_2~ | 修被动方应用           |
| 最终 ACK 丢失                | 对端重传 FIN                            | TIME_WAIT 期间重新 ACK |

- ~CLOSE_WAIT~ 堆积是 *收到 FIN 那一方应用的 bug* （收到 FIN 却不 ~close()~ ），不是网络问题； ~FIN_WAIT_2~ 堆积是它的镜像 —— 同一件事在主动方一侧的表现。
- 谁先发 FIN，谁就是主动关闭方；客户端和服务端都可能，不必是服务端。
- Keepalive 负责发现长期无数据的半开连接，开始探测的时机由内核参数决定，粒度粗，不能当快速断线检测；要快速发现通常用应用层心跳。
- 半开连接：一端宕机，另一端仍停在 ~ESTABLISHED~ ，只有发数据收到 RST、或 Keepalive 探测才能发现。

* Misconceptions

** 四次挥手为什么是四次？

原来只会背四个步骤，答不出「为什么」。实际逻辑：全双工两个方向各自独立关闭，每个方向一轮 FIN + ACK，所以是 4；B 没有待发数据时 ACK 与 FIN 合并，就只有 3 个报文。

** 「连接」是物理连接吗？

不是。连接是两端各自维护的状态机，中间设备只转包；握手确认的是「此刻双向可达」，不是某条固定通路。

* My Take :mine:

> 连接不是真正的物理连接，而是两端各自维护一个状态机。

> 直白说就是两端都需要一来一去确认才保险，这样沿路路由、两端机器各自发不出，都能测出来。多几个来回当然也可以，但最关键的「两端都验证过一来一回」已经测完通路，再来回就没必要了。

> 可以简单理解为两边都要通知不再发数据（FIN），再互相对对方的 FIN 作出 ACK。
