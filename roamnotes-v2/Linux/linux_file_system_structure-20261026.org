#+title: Linux File System Structure
#+filetags: :Linux:

* VFS 与四个对象
虚拟文件系统（Virtual File System，VFS）是内核里的一层通用接口： ~open~ 、 ~read~ 、 ~stat~ 、 ~rename~ 等系统调用都先到 VFS，再由具体文件系统（ext4、xfs、btrfs、tmpfs、NFS、 =/proc= ）实现。管道、socket、设备文件也挂在 VFS 下，所以都能用同一套 fd 接口操作。

VFS 用四个对象描述文件：

| 对象 | 是什么 | 生命周期 |
|---|---|---|
| 超级块（superblock） | 一个已挂载的文件系统：块大小、总量、inode 总数 | 挂载期间 |
| inode（index node） | 一个文件本身：类型、权限、属主、大小、时间戳、链接数、数据块位置。 *不含文件名* | 在磁盘上持久存在；内存中有缓存 |
| 目录项（dentry） | 路径中的一个名字到 inode 的映射。目录的内容就是一组「名字 → inode 号」 | 只在内存里，用作路径查找的缓存 |
| 文件（file） | 一次 ~open~ 的结果：偏移量、打开模式。即「打开文件描述」，见 [[id:937b44b4-497a-466a-924d-0a01a2228266][Linux File Descriptors and Open Files]] | 到最后一个引用它的 fd 关闭 |

- inode 号只在同一个文件系统内唯一；全局标识一个文件要用（设备号, inode 号）。 ~ls -i~ 、 ~stat~ 可以看到。
- 内存中的 inode 和目录项放在内核的 slab 缓存（ =/proc/slabinfo= 中的 =dentry= 、 =ext4_inode_cache= 等）里，不在页缓存里；文件内容才在页缓存里，见 [[id:a20150eb-3731-4848-8a33-c55c4a318b7b][Linux Page Cache and Writeback]]。这些 slab 缓存内存紧张时同样可以回收，在 =/proc/meminfo= 中计入 =SReclaimable= 。
- ext4 的 inode 数量在 ~mkfs~ 时固定：大量小文件可能先耗尽 inode，此时写入报「No space left on device」，但 ~df -h~ 显示还有空间，要看 ~df -i~ 。xfs、btrfs 动态分配 inode，没有这个问题。

* 链接、删除与重命名
因为文件名属于目录项而不属于 inode，一个 inode 可以有多个名字：

| | 硬链接（hard link） | 符号链接（symbolic link） |
|---|---|---|
| 本质 | 另一个指向同一 inode 的目录项，inode 的链接数加一 | 一个独立的小文件，内容是目标路径 |
| 跨文件系统 | 不能（inode 号只在本文件系统内有意义） | 能 |
| 指向目录 | 不能（防止目录树成环） | 能 |
| 目标删除后 | 不受影响，数据还在 | 变成悬空链接 |

- 删除（ ~unlink~ ）只删一个目录项、链接数减一。链接数为 0 *且* 没有进程打开它时，inode 和数据块才释放。
- 坑：删掉一个仍被进程打开的大日志文件， ~df~ 不会下降，因为空间要等进程关闭文件才释放。 ~ls -l /proc/<pid>/fd~ 中这类文件显示为 =(deleted)= ， ~lsof +L1~ 列出全部。处理办法是重启进程或通知它重新打开日志；要立即腾出空间，可以 ~truncate -s 0 /proc/<pid>/fd/<n>~ 。
- ~rename~ 在同一文件系统内是原子的：目标名要么还指向旧文件，要么已指向新文件，不会出现中间状态。「写临时文件再 ~rename~ 覆盖」是安全更新文件的基础，完整步骤还需要 ~fsync~ ，见 [[id:c7ce9028-6f2b-467d-a4e2-989926573aa4][Linux File I/O Buffering and Durability]]。

* 日志与崩溃一致性
写一个文件要改好几处元数据（inode、块位图、目录项），中途断电会留下不一致的状态。早期文件系统重启后要用 ~fsck~ 扫描整个文件系统修复，大盘要几十分钟。

日志文件系统（journaling file system）先把要做的元数据修改写进磁盘上的日志（journal），提交后再写到原位置；崩溃后只需重放或丢弃日志中的事务，恢复时间与盘的大小无关。ext4 的三种模式：

| ~data=~ 模式 | 写入日志的内容 | 崩溃后 |
|---|---|---|
| ~journal~ | 元数据和文件数据 | 最安全，数据写两次，最慢 |
| ~ordered~ （默认） | 只有元数据；但先写数据块，再提交引用它们的元数据 | 不会出现文件指向未写完的块；最近写入的数据可能丢失 |
| ~writeback~ | 只有元数据，不保证顺序 | 文件中可能出现旧的垃圾数据 |

- 日志保证的是 *文件系统结构* 不坏，不保证你刚 ~write~ 的数据已经落盘。数据要持久，仍需 ~fsync~ 。
- 常见文件系统：ext4（日志，最通用）；xfs（日志，大文件和并行 I/O 表现好，RHEL 默认）；btrfs（不用日志，而是写时复制（copy-on-write）：新数据写到新位置再切换指针；另有数据校验和、快照、透明压缩，本机根分区就是 btrfs）。

* Linux tmpfs
:PROPERTIES:
:ID:       52cc876c-a7de-45de-a3d8-c28b12c08f78
:END:
tmpfs 是只存在于内存中的文件系统：文件内容就是页缓存中的页，没有底层磁盘，重启即丢失。

- 它的页属于共享内存（shmem），在 =/proc/meminfo= 中计入 =Shmem= （也计入 =Cached= ，但不能像普通页缓存那样直接丢弃）；内存紧张时可以像匿名页一样换出到 swap。回收方式的区别见 [[id:c2e41773-cd6c-4697-84fd-33a1178a0407][Linux Memory Mappings]] 中的映射分类。
- 默认容量上限为物理内存的一半，用挂载选项 ~size=~ 调整；上限只是上限，没写入的部分不占内存。
- 用途： =/dev/shm= （POSIX 共享内存的对象就是其中的文件，见 [[id:681a06e2-6aad-4c49-881c-286cc53542f0][Linux Shared Memory]]）、 =/run= 、有的发行版的 =/tmp= ，以及编译等产生大量临时文件的场合。内核还在内部挂了一个看不见的 tmpfs，用来支撑共享匿名映射和 ~memfd_create~ 。
- 坑：写进 tmpfs 的数据就是内存占用，忘了删除就一直占着；Docker 容器的 =/dev/shm= 默认只有 64 MiB（本机容器配置为 1 GiB），数据量大的程序会意外写满。
