#+title: Linux I/O Models and Multiplexing
#+filetags: :Linux:

* 两个阶段、两组概念
以从 socket 读数据为例，一次输入分两个阶段：① 等数据到达内核（对端发来报文）；② 把数据从内核拷到用户缓冲区。两组常被混用的概念分别回答不同的问题：

- 阻塞 / 非阻塞：阶段 ① 数据还没到时，调用怎么办。阻塞就睡眠等待；非阻塞（fd 设了 ~O_NONBLOCK~ ）立即返回 ~EAGAIN~ 。 ~O_NONBLOCK~ 是打开文件描述上的状态标志，共享同一描述的 fd 一起受影响，见 [[id:937b44b4-497a-466a-924d-0a01a2228266][Linux File Descriptors and Open Files]]。
- 同步 / 异步：阶段 ② 由谁完成。同步是应用自己调用 ~read~ 完成拷贝；异步是应用提交请求后去做别的事，内核把两个阶段都做完再通知「已完成」。

| 模型 | 阶段 ① 等数据 | 阶段 ② 拷贝 | 归类 |
|---|---|---|---|
| 阻塞 I/O | ~read~ 中睡眠 | ~read~ 中完成 | 同步 |
| 非阻塞 I/O | 反复调用 ~read~ ，得到 ~EAGAIN~ 就稍后再试 | ~read~ 中完成 | 同步 |
| I/O 多路复用 | 在 ~select~ / ~poll~ / ~epoll_wait~ 中等多个 fd 中任一就绪 | 就绪后调用 ~read~ | 同步 |
| 信号驱动 I/O | 就绪时内核发 ~SIGIO~ | 信号处理后调用 ~read~ | 同步 |
| 异步 I/O | 不等，提交后立即返回 | 内核完成，通过完成队列通知 | 异步 |

** 误解：多路复用是异步 I/O
旧笔记把 I/O 多路复用写成「异步、非阻塞 IO」。多路复用只是把「等就绪」集中到一个调用里，就绪后的 ~read~ 仍由应用自己完成拷贝，是同步 I/O。真正的异步 I/O 在 Linux 上是 io_uring（以及只适用于 ~O_DIRECT~ 的旧 Linux AIO）。

* 为什么要多路复用
C10K 问题：每个连接一个线程（阻塞 I/O），一万个连接就是一万个线程，每个线程有自己的栈，线程之间频繁切换，见 [[id:706d7e91-8a8f-466f-b871-602e2efcd187][Linux Context Switching]]。多路复用让一个线程等待成千上万个 fd，只处理已就绪的那些：这就是事件循环（event loop），nginx、Redis、libuv、Python asyncio 都建立在它上面。

| | ~select~ | ~poll~ | ~epoll~ |
|---|---|---|---|
| 关注的 fd 集合 | 每次调用都整体传入（位图） | 每次调用都整体传入（数组） | 用 ~epoll_ctl~ 登记一次，内核保存 |
| fd 数量限制 | fd 号小于 ~FD_SETSIZE~ （1024） | 无 | 无 |
| 每次调用的代价 | 拷贝并扫描全部 fd，O(n) | 同左 | 只返回就绪的 fd，与就绪数成正比 |
| 可移植性 | POSIX | POSIX | Linux 专有（BSD 上对应 kqueue） |

连接多而活跃的少时（大量空闲长连接）， ~epoll~ 的优势最大；fd 很少时三者差别不大。

* 水平触发与边缘触发
~epoll~ 有两种通知方式。本机用管道实测：写入 10 字节，读走 5 字节后再次 ~epoll_wait~ ：

| | 读一半后再等 | 又写入 1 字节后再等 |
|---|---|---|
| 水平触发（level-triggered，默认） | 仍报告可读 | 报告可读 |
| 边缘触发（edge-triggered， ~EPOLLET~ ） | *不报告* ，剩下的 5 字节没人提醒 | 报告可读 |

- 水平触发：只要还有数据就一直报告，没读完下次还会通知，不易出错。
- 边缘触发：只在状态变化（新数据到达）时报告一次。必须把 fd 设为非阻塞，并循环 ~read~ 直到返回 ~EAGAIN~ ；否则剩余数据要等对端再发数据才会被通知，连接看起来像卡住了。好处是同一批数据不会被重复通知。
- 多线程共用一个 epoll 实例时，用 ~EPOLLONESHOT~ 保证一个 fd 同一时刻只被一个线程处理（处理完再用 ~EPOLL_CTL_MOD~ 重新启用）。

* 普通文件不能多路复用
- 普通文件总是被报告为「就绪」：把它加入 ~epoll~ 直接返回 ~EPERM~ （本机实测）， ~select~ / ~poll~ 则总是立即返回可读写。
- ~O_NONBLOCK~ 对普通文件不起作用：页缓存未命中时 ~read~ 照样阻塞，线程处于 D 状态等磁盘。旧资料说「内核缓存保证普通文件 I/O 不会阻塞」是错的。
- 所以事件循环里的文件读写要么交给线程池（libuv、Python 的 ~run_in_executor~ ），要么用 io_uring。

* io_uring
io_uring（5.1 起）是真正的异步接口：应用和内核共享两个环形队列，应用往提交队列放请求，内核把结果放进完成队列。

- 文件、socket 都支持，对普通文件也是真正的异步。
- 一次 ~io_uring_enter~ 可以提交和收割许多请求，系统调用次数大减；开启 ~IORING_SETUP_SQPOLL~ 后由内核线程轮询提交队列，热路径上可以完全不进内核。
- 坑：io_uring 是近年内核漏洞的主要来源之一，有的容器和云环境出于安全原因禁用它；6.6 起可用 ~kernel.io_uring_disabled~ 整体关闭（本机 6.5 尚无此参数，io_uring 可用）。用前确认目标环境支持，并保留 epoll 的回退路径。
- 低延迟系统通常不用以上任何「等待」机制，而是让线程独占一个核忙轮询（ ~epoll_wait~ 超时设为 0 或内核旁路），用 CPU 换掉睡眠和唤醒的延迟。
