*** Front
What does ~std::move(x)~ actually do at run time? What happens when the type of ~x~ has no move constructor?

*** Back
Nothing at run time: it is ~static_cast<T&&>(x)~, which turns an lvalue into an xvalue so overload resolution can pick the move constructor or move assignment. Without a move overload, the copy overload (~const T&~) binds and the object is copied.

*** Front
When should a class declare none of the five special member functions, and when should it declare all five? Name the five.

*** Back
- Rule of zero: when its members already manage themselves (~std::string~, ~std::vector~, smart pointers), declare none; the generated ones are correct.
- Rule of five: when it manages a resource directly and needs to declare any one, declare all five: destructor, copy constructor, copy assignment, move constructor, move assignment.

*** Front
A class has a move constructor that is not ~noexcept~. What does ~std::vector~ do with its elements when it reallocates, and why?

*** Back
It copies them instead of moving. Reallocation keeps the strong exception guarantee: if a move threw halfway, the old buffer would already be damaged, so it only moves when the move cannot throw. Mark move operations ~noexcept~; ~= default~ does so automatically when the members allow it.

*** Front
Why is ~return std::move(local);~ worse than ~return local;~ for a local object?

*** Back
The cast makes the return expression no longer just the name of the local, so the compiler cannot apply NRVO (construct the result in place) and must move. Plain ~return local;~ gets NRVO in practice, and if NRVO is not applied it still moves, never copies. GCC warns with =-Wpessimizing-move=.

*** Front
What does a virtual call cost compared with a direct call, and what do low-latency hot paths use instead?

*** Back
Load the object's vptr, load the function pointer from the vtable slot (two dependent loads), then an indirect call: no inlining unless the compiler can devirtualize, and a possible branch mispredict. Hot paths use static polymorphism (templates, CRTP) or ~std::variant~; ~final~ also lets the compiler devirtualize.

*** Front
Why prefer ~std::make_shared<T>(args)~ over ~std::shared_ptr<T>(new T(args))~? What is its one memory drawback?

*** Back
- One allocation for the object and the control block instead of two.
- No leak if evaluating another argument of the same call throws.

Drawback: since object and control block share one allocation, the memory of a large ~T~ is not freed until the last ~weak_ptr~ is gone too, even though ~T~ was destroyed when the strong count hit 0.

*** Front
A parent holds ~shared_ptr~ to its children and each child holds ~shared_ptr~ to its parent. What goes wrong, how do you fix it, and how does a child then use its parent?

*** Back
Both strong counts stay above zero forever, so neither destructor runs: a leak. Make the back-pointer (child → parent) a ~std::weak_ptr~. To use it: ~if (auto p = parent.lock()) { ... }~. ~lock()~ checks and obtains a ~shared_ptr~ atomically; checking ~expired()~ first and then using it is a race.

*** Front
"~shared_ptr~ is thread-safe." Which parts are, and which are not?

*** Back
Only the control block: copying and destroying different ~shared_ptr~ objects that share one object update the counts atomically. Not safe:
- concurrent access to the pointed-to object (needs its own lock);
- two threads assigning to the same ~shared_ptr~ variable (a data race; use ~std::atomic<std::shared_ptr<T>>~, C++20).

** Race in a thread-safe stack interface
:PROPERTIES:
:ANKI_NOTE_TYPE: CC Basic
:ANKI_NOTE_ID: 1793078044816
:ANKI_NOTE_HASH: ca957866c326f9a4e4fad46dae0c1fdc
:END:

*** Front
Every member function of a stack locks the same mutex. Why is ~if (!s.empty()) { v = s.top(); s.pop(); }~ still a race, and how do you fix it?

*** Back
Each call is atomic, but the check-then-act sequence is not: two threads can both read the same ~top()~ and then pop two elements, one of which nobody read. Fix the interface, not the locking: merge ~top()~ and ~pop()~ into one ~pop()~ that returns the value, as ~std::shared_ptr<T>~ or through a ~T&~ argument, so a throwing copy cannot lose an element that was already removed.

Source: C++ Mutexes, Locks and Deadlock

** Locking two mutexes without deadlock
:PROPERTIES:
:ANKI_NOTE_TYPE: CC Basic
:ANKI_NOTE_ID: 1793078044830
:ANKI_NOTE_HASH: eb8779b2ab432bce2b0d8e21b24b86af

*** Front
~swap(X& lhs, X& rhs)~ must lock both objects' mutexes. How do you write the locking so two threads calling ~swap(a, b)~ and ~swap(b, a)~ cannot deadlock? What special case must be checked first?

*** Back
#+begin_src cpp
if (&lhs == &rhs) return;            // locking the same mutex twice is UB
std::scoped_lock lk(lhs.m, rhs.m);   // C++17: both or neither, any order
#+end_src
~std::scoped_lock~ acquires several mutexes in one step with a deadlock-avoidance algorithm. When locks are taken separately in different functions, use a fixed global order instead.

*** Front
Why is double-checked locking on a plain pointer (~if (!p) { lock; if (!p) p = new T; }~) broken, and what are the two correct standard alternatives?

*** Back
The unlocked first check reads ~p~ while another thread writes it: a data race, and a reader can see the pointer before the object it points to is constructed. Use:
- a function-local ~static~ (thread-safe since C++11; the Meyers singleton);
- ~std::call_once~ with a ~std::once_flag~.

If a pointer is really needed, make it ~std::atomic<T*>~ with acquire / release.

A consumer writes ~cv.wait(lk); int v = q.front(); q.pop();~. What can go wrong, and what should it write?

*** Back
The thread can wake while the queue is still empty: a spurious wake-up, or another consumer took the item first. ** Release / acquire publication
:PROPERTIES:

*** Front
Thread 1 fills a plain buffer and then sets ~std::atomic<bool> ready~ to true; thread 2 waits for ~ready~ and then reads the buffer. Which memory orders are needed on the store and the load, and what can go wrong with ~relaxed~ on both?

*** Back
Store with ~memory_order_release~, load with ~memory_order_acquire~. When the acquire load reads ~true~, everything thread 1 wrote before the release store is visible to thread 2 (a happens-before edge). With ~relaxed~ only ~ready~ itself is atomic: thread 2 may see ~true~ but stale buffer contents. It often happens to work on x86, whose plain loads and stores already behave as acquire / release, and breaks on ARM.

Source: C++ Memory Model and Atomics

** Compound expressions on atomics
:PROPERTIES:
:ANKI_NOTE_TYPE: CC Basic
:ANKI_NOTE_ID: 1793078044891
:ANKI_NOTE_HASH: 09d063748f353ea61c0775dc8479e1d4

*** Front
With ~std::atomic<int> x;~ shared by several threads, why is ~x = x + 1;~ wrong? How do you double ~x~ atomically?

*** Back
Each operation is atomic, but the expression is an atomic load followed by an atomic store; another thread's update between them is lost. Use ~x.fetch_add(1)~ (or ~++x~). Doubling has no ~fetch_~ form (~x *= 2~ does not compile), so use a CAS loop:
#+begin_src cpp
int expected = x.load();
while (!x.compare_exchange_weak(expected, expected * 2)) {}
#+end_src
A failed CAS writes the current value into ~expected~, so the loop needs no extra load.

Source: C++ Memory Model and Atomics

*** Front
Each thread increments only its own counter in ~long counters[8];~, yet the loop scales badly with more threads. Why, and what is the fix?

*** Back
False sharing: the counters share a cache line, so every write needs exclusive ownership of that line and it bounces between cores as if the data were shared. ** ABA problem
:PROPERTIES:
:ANKI_NOTE_TYPE: CC Basic
:ANKI_NOTE_ID: 1793078044943
:ANKI_NOTE_HASH: bac7f51ce3b4a17c51ed1569815dc099
:END:

*** Front
In a lock-free stack, ~pop~ reads ~head == A~ and ~A->next == B~, then CASes ~head~ from ~A~ to ~B~. Describe the ABA failure and two ways to prevent it.

*** Back
The thread is suspended after reading. Others pop ~A~ and ~B~, free them, and push a new node that reuses ~A~'s address. The CAS sees ~head == A~ and succeeds, installing the freed ~B~. Prevent it by:
- never reusing a node while any thread may still hold it (hazard pointers, epoch-based reclamation);
- pairing the pointer with a version counter updated by a double-width CAS.

Source: C++ Lock-free Data Structures

** Choosing lock-free or lock-based
:PROPERTIES:
:ANKI_NOTE_TYPE: CC Basic
:ANKI_NOTE_ID: 1793078044961
:ANKI_NOTE_HASH: 4ab8a01a2d7d639eb00472467f16269e
:END:

*** Front
When is a lock-free structure worth it over a mutex-based one, and why is it not automatically faster?

*** Back
Worth it when a descheduled lock holder blocking everyone is unacceptable: latency-sensitive paths such as single-producer single-consumer ring buffers in trading systems; it also cannot deadlock. Not automatically faster: contended atomics bounce cache lines, an uncontended mutex is cheap, and correctness (memory reclamation, ABA, memory orders) is far harder. Measure worst-case and average latency and throughput before switching.

Source: C++ Lock-free Data Structures
