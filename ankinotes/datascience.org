** Polars Eager Methods and the Lazy Engine

*** Front
Eager Polars methods such as ~DataFrame.with_columns~ are implemented as ~lazy()~ plus an immediate collect. Why is ~pl.read_csv(...)~ followed by ~select~ still worse than ~pl.scan_csv(...)...collect()~?

*** Back
Each eager call is a separate one-node query, so there is no whole pipeline for the optimizer to rearrange (plan-level optimizations are off). ~read_csv~ therefore parses every column first; the lazy query can push the column selection into the scan and parse only the needed columns.

Expression evaluation itself is the same Rust code in both modes.

** Nulls in Integer Columns: Polars vs pandas
:PROPERTIES:
:ANKI_NOTE_TYPE: CC Basic
:ANKI_NOTE_ID: 1793029835540

*** Front
~pd.Series([1, None])~ becomes ~float64~, but ~pl.Series([1, None])~ is ~Int64~. Why can Polars keep the integer type?

*** Back
Polars stores each column in the Arrow format: a buffer of values plus a validity bitmap (1 bit per row) that marks nulls. Missing values need no sentinel, so any type can hold nulls. pandas' default NumPy path uses NaN as the sentinel, which forces a float type.
